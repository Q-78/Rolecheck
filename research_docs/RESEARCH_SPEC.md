# RoleCheck 研究规范

**项目名称：** RoleCheck  
**暂定英文题目：** *RoleCheck: Plug-and-Play Multi-Agent Initialization Auditing and Minimal Repair via Counterfactual Role-Value Prediction*  
**版本：** v0.1  
**日期：** 2026-08-01  
**文档性质：** 课题定义与方法边界规范，不包含具体 Benchmark、模型、样本量或工程排期。

---

# 1. 研究目标

本课题研究一个位于 LLM 多智能体系统初始化器与执行框架之间的可插拔审计层。给定任务和初始化器生成的团队，RoleCheck 在角色正式参与当前任务的完整执行前：

1. 将不同框架的角色描述归一化为统一 Role Contract；
2. 检测角色自身、角色之间及角色与协议之间的潜在缺陷；
3. 预测每个角色相对于当前任务、团队和协议的操作性反事实保留价值；
4. 针对被诊断角色生成有限、缺陷条件化的修复候选；
5. 预测各修复候选的操作性反事实修复价值；
6. 根据预测收益、不确定性、成本与最小干预原则选择 KEEP、REWRITE 或 REMOVE；
7. 将修改后的团队配置交回原有 MAS 运行时。

本课题的算法核心是：

> **当前任务执行前、团队条件和协议条件下的反事实角色价值预测。**

角色缺陷诊断负责解释和生成候选，角色修复是价值预测的下游应用。

---

# 2. 研究动机

现有 MAS 初始化与设计工作已经能够自动生成或搜索 Agent 数量、角色职责、基础模型或能力配置、通信依赖、协作拓扑和系统 Prompt。但初始化输出仍可能包含：

- 角色与当前任务无关；
- 多个角色职责重叠；
- 决策权限冲突；
- 上游没有提供下游所需信息；
- 输出格式不能被后续节点消费；
- 角色规范含糊或过载；
- 角色单独表现较强，却对当前团队没有新增价值；
- 角色静态上看似冗余，但实际上提供独特行为或错误互补；
- 低贡献角色可能可通过小幅修复改善，也可能由模型能力上限造成而不可修复。

因此，角色的“语义合理性”“个体能力”和“团队价值”是三个不同概念。RoleCheck 的研究对象是第三个概念，并利用前两个概念作为预测信息。

# 3. 核心术语

## 3.1 初始化器

初始化器记为：

\[
\mathcal I(x)\rightarrow C
\]

其中 \(x\) 是任务实例或任务描述，\(C\) 是初始化后的团队配置。RoleCheck 不要求访问初始化器内部梯度、隐藏状态或训练过程。只要初始化器能够导出团队配置，即可通过适配器接入。

## 3.2 团队配置

团队配置定义为：

\[
C=(A,R,M,T,G,\pi)
\]

- \(A=\{a_1,\ldots,a_n\}\)：Agent 实例；
- \(R=\{r_1,\ldots,r_n\}\)：角色规范；
- \(M\)：每个 Agent 的基础模型配置；
- \(T\)：工具及权限；
- \(G\)：通信、依赖或工作流结构；
- \(\pi\)：执行、通信、停止与聚合协议。

第一版方法可只允许修改角色 Prompt 和团队成员资格，但审计必须将 \(M,T,G,\pi\) 视为上下文，因为它们会改变角色价值。

## 3.3 角色配置

角色不是角色名称或一句 Prompt。角色定义为：

\[
r_i=(name_i,goal_i,responsibilities_i,prompt_i,inputs_i,outputs_i,authority_i,dependencies_i,model_i,tools_i)
\]

角色的价值不应写成 \(Q(r_i)\)，而应写成：

\[
Q(r_i\mid x,C_{-i},\pi)
\]

## 3.4 当前任务执行前

“执行前”有两种设置，必须分别报告。

### Strict Task-Level Pre-Execution

预测当前任务 \(x\) 的角色价值时，不允许访问：

- 被审计角色在 \(x\) 上的输出；
- 该角色在 \(x\) 上的正确性；
- 完整团队在 \(x\) 上的真实效用；
- 该任务的 Gold 答案；
- 当前任务上的实际移除、替换或修复结果；
- 当前任务执行轨迹。

允许访问：

- 当前任务文本及可公开元数据；
- 团队与角色合同；
- 模型、工具、拓扑和协议配置；
- 由训练任务或历史任务建立的画像。

### Probe-Assisted Pre-Deployment

允许在与正式测试任务隔离的校准任务上运行角色，建立能力画像、格式遵循率、行为相似度、历史反事实贡献、历史修复响应、成本和延迟画像。此设置仍然禁止查看当前正式测试任务的角色输出和真实结果。

# 4. 效用与操作性反事实

## 4.1 团队效用

定义：

\[
U(x,C,\pi)\in\mathbb R
\]

效用可以是任务成功、准确率、可执行测试得分、安全得分，或性能与成本的组合。RoleCheck 不将效用永久限定为二值正确性。

可定义净效用：

\[
J(x,C,\pi)=U(x,C,\pi)-\lambda_c Cost(C)-\lambda_l Latency(C)
\]

任何论文结论必须明确其使用的是任务效用还是净效用。

## 4.2 保留价值

对已在团队中的 Agent \(a_i\)：

\[
\Delta_i^{keep}(x,C,\pi)=J(x,C,\pi)-J(x,C\setminus\{a_i\},\pi_{-i})
\]

其中 \(\pi_{-i}\) 是预先声明的移除协议。移除角色后如何处理断开的依赖、消息和聚合权，必须由协议定义，而不能临时决定。

解释：

- 正值：保留该角色有利；
- 零附近：角色没有可观测新增价值；
- 负值：移除后更好，角色可能有害或成本无效。

## 4.3 修复候选价值

对候选修复 \(r'_{ik}\)：

\[
\Delta_{ik}^{repair}(x,C,\pi)=J(x,C_{i\leftarrow r'_{ik}},\pi)-J(x,C,\pi)
\]

修复价值必须绑定具体候选 \(r'_{ik}\)。禁止将“修复后的角色”视为未定义的无限空间。

## 4.4 操作性反事实

本课题使用“操作性反事实”而非普遍因果效应。含义是：

> 在固定任务、模型、工具、协议和其他角色的受控配置比较中，由预先规定的角色干预产生的效用差。

使用该术语的必要条件：

- 明确干预对象；
- 明确移除或替换协议；
- 除目标干预外尽可能保持配置不变；
- 声明随机性控制与重放策略；
- 不把相关性预测表述为已识别的因果效应。

# 6. 缺陷诊断与价值预测的关系

RoleCheck 将角色分析分成三层。

## 6.1 内在角色缺陷

单独查看角色合同即可发现或怀疑的问题：欠描述、Prompt 内部冲突、角色过载、能力或工具不匹配。

## 6.2 团队关系缺陷

只有结合其他角色和协议才能发现：任务无关、角色冗余、权限冲突、依赖缺口、协议不匹配、团队职责覆盖缺口。

## 6.3 系统价值结果

通过操作性反事实定义：无贡献、有害、不可修复、成本无效。

必须保持：

\[
DefectProbability \neq CounterfactualValue
\]

缺陷诊断用于解释风险、构造特征和生成定向修复候选；价值预测用于决定是否干预、在修复候选间排序，并防止静态规则造成误删和过度治疗。

# 7. 方法模块

## 7.1 Initializer Adapter

职责：

- 从不同框架导出团队配置；
- 将框架特有字段映射到统一结构；
- 声明无法表达的信息；
- 不修改原初始化器内部逻辑。

输出：

\[
C^{raw}\rightarrow C^{canonical}
\]

## 7.2 Role Contract Normalizer

职责：

- 从自然语言 Prompt、配置文件和工作流节点中提取 Role Contract；
- 保存原始文本和结构化字段；
- 标记推断字段与显式字段；
- 输出抽取置信度；
- 不在归一化阶段擅自优化 Prompt。

## 7.3 Static Role Defect Auditor

输入任务需求、Role Contract、团队关系图和协议规范，输出：

\[
P(d_k\mid x,C,r_i,\pi)
\]

该模块可以使用规则、语义模型或 LLM，但不能直接把主观判断当作真实贡献标签。

## 7.4 Counterfactual Keep-Value Predictor

\[
f_{keep}(x,C,r_i,\pi,H)\rightarrow(\widehat{\Delta}_i^{keep},\sigma_i^{keep})
\]

\(H\) 表示可选历史画像。预测器不得访问当前任务上的真实执行结果。

## 7.5 Defect-Conditioned Repair Candidate Generator

\[
g(x,C,r_i,d_i,constraints)\rightarrow\mathcal R_i
\]

输出有限候选集合：

\[
\mathcal R_i=\{r'_{i1},\ldots,r'_{iK}\}
\]

约束：

- 每个候选应针对已诊断缺陷；
- 保持原角色目标中无问题的部分；
- 显式记录修改内容；
- 候选必须符合原运行时接口；
- 候选生成器不负责最终选择。

## 7.6 Repair-Value Predictor

\[
f_{repair}(x,C,r_i,r'_{ik},\pi,H)\rightarrow(\widehat{\Delta}_{ik}^{repair},\sigma_{ik}^{repair})
\]

该模块预测指定候选的收益，不预测抽象的“最佳修复”。

## 7.7 Risk-Aware Minimal Intervention Policy

动作：

\[
o_i\in\{KEEP,REWRITE,REMOVE\}
\]

候选保守价值：

\[
LCB_{ik}^{repair}=\widehat{\Delta}_{ik}^{repair}-\beta\sigma_{ik}^{repair}-\lambda Cost(r'_{ik})
\]

移除可依据保留价值的置信上界：

\[
UCB_i^{keep}=\widehat{\Delta}_i^{keep}+\beta\sigma_i^{keep}
\]

原则性决策：

- 若最佳修复候选的 LCB 高于阈值，则 REWRITE；
- 若 \(UCB_i^{keep}\) 仍显著为负，则 REMOVE；
- 其余情况 KEEP；
- 在信息不足、合同抽取失败或协议不明确时 abstain，并默认 KEEP。

第一版不允许一次修改多个强耦合角色后仍把收益归因于单个角色。多角色联合修复属于扩展问题。

# 8. 最小干预原则

“Minimal Repair”必须同时满足：

1. **对象最小：**只修改被可靠诊断且具有预期正收益的角色；
2. **内容最小：**保留无问题的角色目标、权限与接口；
3. **结构最小：**不修改无关模型、工具、拓扑和协议；
4. **次数最小：**避免无界迭代重写；
5. **风险最小：**高不确定性时默认不干预；
6. **成本可计量：**审计、候选生成和修复成本必须被纳入净收益；
7. **可回滚：**保留原始合同、版本和修改差异。

最小化不等于字符编辑距离最小。语义职责和接口保持是更高优先级。

---

# 9. 可插拔性的操作定义

只有同时满足下列条件，才可主张 Plug-and-Play：

1. 输入为统一团队配置与 Role Contract；
2. 不依赖初始化器的私有梯度、内部奖励或隐藏状态；
3. 不要求重写初始化器核心代码；
4. 通过薄适配器接入；
5. 输出仍能被原运行时消费；
6. 核心审计器可在至少两个不同初始化来源之间复用；
7. 框架专用规则必须被明确隔离在 Adapter 中；
8. 接入成本和不支持字段需要被报告。

“可以写一个适配器”本身不足以证明可插拔；必须验证核心逻辑没有被每个框架重新设计。

# 10. 核心研究问题

## RQ1：角色价值是否具有显著的任务、团队和协议条件性？

研究角色名称、语义质量或个体能力是否不足以解释团队贡献，以及团队关系信息能否提供额外预测信息。

## RQ2：能否在当前任务完整执行前预测角色保留价值？

目标是预测：

\[
\widehat{\Delta}^{keep}_i\approx\Delta^{keep}_i
\]

并区分正贡献、无贡献和有害角色。

## RQ3：能否预测和排序有限修复候选的真实价值？

研究修复候选的价值是否可由任务、团队、缺陷和编辑信息提前预测。

## RQ4：不确定性感知的最小干预能否减少有害修改？

研究校准、不确定性和 abstention 是否能降低健康角色误改、无效修复和负收益修复。

## RQ5：核心审计器能否跨初始化器复用？

研究同一表示和价值预测逻辑是否能在不同团队生成机制之间迁移。

# 11. 核心假设

## H1：关系性价值假设

Task + Role + Team + Protocol 比 Role-only 和 Individual-capability-only 更能预测真实角色贡献。

## H2：缺陷—价值非等价假设

静态缺陷概率与真实团队贡献相关，但不能相互替代。

## H3：贡献—可修复性非等价假设

低贡献角色中只有部分能够通过角色合同或 Prompt 修复；其他问题源于模型、工具、拓扑或协议。

## H4：选择性优于普遍重写假设

由预测价值指导的选择性修复，比随机修复、全部修复和仅由 LLM 主观判断的修复更安全有效。

## H5：不确定性抑制过度治疗假设

保守置信界与 abstention 能降低健康角色误删和有害重写。

## H6：共享审计空间假设

不同初始化器输出可映射到共享角色合同和团队关系空间，从而支持核心审计器复用。

# 12. 评价维度（概念级）

本规范暂不确定具体数据集和模型，但后续评价必须覆盖以下维度。

## 12.1 价值预测

- 正贡献识别；
- 有害角色识别；
- 数值误差；
- 候选排序；
- 概率校准；
- 风险—覆盖关系。

## 12.2 缺陷诊断

- 多标签缺陷识别；
- 异常角色定位；
- 健康角色误报率；
- 解释与合同证据的一致性。

## 12.3 干预结果

- 修复成功率；
- 有害修复率；
- 不必要修改率；
- 移除错误率；
- 净效用变化；
- 审计与修复成本。

## 12.4 泛化与可插拔性

- 未见任务；
- 未见角色名称；
- 未见基础模型；
- 未见初始化器；
- 不同执行协议；
- 合同字段缺失或不完整。

---

# 13. 数据与信息边界

任何后续数据构建必须遵守：

- 同一原始任务及其完整、移除、损坏、修复版本必须位于同一数据划分；
- 当前任务的实际角色输出不能作为执行前预测特征；
- 当前任务的真实效用、移除效用和修复效用只用于标签和最终评价；
- 测试集贡献统计不能进入历史画像；
- 修复候选的真实表现不能被用于生成同一测试实例上的选择特征；
- 角色名称不能成为唯一标识，应保留职责与合同语义；
- 初始化器来源可作为分析变量，但避免模型直接记住“某初始化器通常较差”。

---

# 14. 第一版方法边界

允许：

- 审计已初始化角色；
- 结构化角色合同；
- 预测 KEEP 和指定修复候选的价值；
- 修改角色 Prompt 或合同中的职责与输入输出描述；
- 移除角色；
- 拒绝判断并默认保留。

暂不允许：

- 新增全新角色；
- 更换基础模型；
- 分配新工具；
- 修改通信拓扑；
- 修改执行轮次和停止策略；
- 修改聚合器；
- 联合重写整个团队；
- 强化学习训练完整编排器；
- 当前任务执行后的轨迹故障定位；
- 声称严格因果识别。

这些扩展可在核心问题成立后单独研究。

# 15. 成功与失败的科学判定

课题核心成立至少需要概念上支持以下链条：

```text
角色价值具有团队条件性
    ↓
执行前信息能预测保留价值
    ↓
修复候选价值可以被排序
    ↓
预测价值能指导更安全的干预
    ↓
核心审计逻辑可跨初始化来源复用
```

可能的负面结论同样有价值：

- 静态信息不足以预测任务级贡献；
- Probe 只能预测平均贡献，不能预测实例级贡献；
- 修复收益主要不可预测；
- 不确定性无法识别高风险干预；
- 角色 Prompt 缺陷不是主要性能瓶颈；
- 不同初始化器不存在共享审计空间。

若价值预测不成立，课题应收缩为角色贡献与缺陷关系分析、角色审计 Benchmark，或角色修复失败机制研究。

# 16. 主要威胁

## 16.1 反事实协议依赖

移除或替换角色可能改变后续上下文。所得价值是特定协议下的操作性量，而非角色的普遍价值。

## 16.2 模型能力与角色缺陷混淆

Prompt 修复不能解决基础模型缺乏知识或推理能力的问题。

## 16.3 标签稀疏和不平衡

大量角色移除可能不改变最终结果，导致零增益占比过高。

## 16.4 聚合器遮蔽贡献

角色可能提供正确信息，但协议无法利用，导致测得价值偏低。应解释为“协议条件价值”。

## 16.5 生成修复候选的偏置

如果候选生成器很弱，修复价值任务的上限会被候选质量限制。

## 16.6 过度治疗

审计器可能修改原本健康的团队，因此拒绝判断和健康团队保护是核心要求。

## 16.7 可插拔性夸大

若每个框架需要大量专用规则、重新标注或重新训练，则可插拔性有限。

# 17. 尚待冻结的研究决策

1. 主任务是否只以保留价值预测为核心，修复价值作为扩展；
2. 效用函数是否首先采用任务正确性，还是直接采用性能—成本净效用；
3. 严格执行前与 Probe-assisted 两种设置的主次；
4. 角色修复是否只修改 Prompt 文本，还是允许修改结构化职责与接口；
5. 移除角色时的依赖修复协议；
6. 是否需要显式建模团队级职责覆盖缺口；
7. 修复候选数量与候选多样性的定义；
8. 跨初始化器时允许多大程度的 Adapter 定制；
9. 不确定性的语义：模型方差、数据外风险或综合风险；
10. 第一版是否支持多个角色同时存在缺陷。
